実験をプロファイリング、カスタマイズ、検査するためのツール

使用量の見積もり：Heron r2 プロセッサーで10分（注：これはあくまで見積もりです。実際の実行時間は異なる場合があります。）

量子コンピューターで良い結果を得るには、うまく設計された回路だけでは不十分です。デバイスの現在の状態、回路のスケジューリング方法、回路が受けるノイズ、そしてジョブが量子処理ユニット（QPU）上でいつどのように実行されるかが、すべて結果の品質に影響します。Qiskit と IBM Quantum® Compute Service は、この情報を可視化する開発者ツールを、順次拡充して提供しています。これらのツールを使えば、本格的な実験に QPU 時間を投入する前にその情報に基づいて対処したり、完了した実験をデバッグしたりできます。

このチュートリアルでは、1つのエンドツーエンドの実験を使って、一般的な開発ワークフローの各段階でこれらのツールを組み合わせる方法を示します。すべてのツールがすべての実験に役立つわけではないため、ご自身のワークロードに関する疑問に答えてくれるツールを選んでください。

ワークフローは次のとおりです。

  1. 線形の横磁場イジングモデルのトロッター化された時間発展のミラー回路を準備します。

  2. ノイズモデルに基づくエラー緩和手法向けに設計された、代替の較正データセットを持つバックエンドを選択します。

  3. デバイスのベンチマーク実験を実行し、トランスパイラーがレイアウトを選択する際に最新のデバイスプロパティを使用するようにします。

  4. スケジュールされた回路のタイミング情報を検査します。

  5. 回路の Pauli-Lindblad ノイズモデルと読み出しノイズモデルを学習します。

  6. ノイズなし、緩和なし、緩和ありのローカルシミュレーションを実行します。ノイズありのシミュレーションでは学習したノイズモデルを使用し、選択したエラー緩和手法でどれだけ改善が見込めるかを示します。このチュートリアルでは、確率的エラーキャンセレーション（PEC）と Twirled Readout Error eXtinction（TREX）を使用します。

  7. QPU で実行せずに使用量の見積もりを取得し、予算に収まるよう実験を調整する必要があるかどうかを確認します。

  8. セッションを開始して較正をトリガーし、実験が最新の較正データを使用するようにします。

  9. Estimator を使用して QPU 上で実験を実行し、ハードウェアの結果をシミュレーションのプレビューと比較します。

  10. 実行スパンを検査して、実行のグループ（チャンク）間に大きな間隔があるかどうかを確認します。

要件​

このチュートリアルを開始する前に、次のものがインストールされていることを確認してください。

  • 可視化サポートを含む Qiskit SDK v2.3 以降

  • qiskit-ibm-runtime v0.52.1 or later (pip install qiskit-ibm-runtime)

  • Qiskit Aer（pip install qiskit-aer）

  • Plotly (pip install plotly)

  • Qiskit Device Benchmarking（pip install git+https://github.com/qiskit-community/qiskit-device-benchmarking.git）

プランの要件

このチュートリアルの一部のステップは、すべてのプランで利用できるわけではありません。

  • ドライランジョブ（ステップ 2.4 と 3.5）は、Flex、Premium、On-Prem プランでのみ利用できます。

  • セッション（ステップ 4.1）は Open プランでは利用できません。代わりにバッチモードで実行するには、ステップ 4.1 で run_calibration = False を設定してください。

ステップ1：回路とオブザーバブルを指定する​

線形の横磁場イジングモデルのトロッター化された時間発展のミラー回路を準備します。回路をミラーリングして回路のユニタリを打ち消し、恒等回路を作ります。理想的な出力は全ゼロ状態であるため、各1量子ビット ZZZ オブザーバブルの理想的な期待値は 1 です。ミラーリングは回路の深さも2倍にするため、ノイズの影響が増幅されます。

import numpy as np
from qiskit.circuit import QuantumCircuit
from qiskit.quantum_info import SparsePauliOp

def construct_ising_circuit(
    num_qubits: int,
    num_trotter_steps: int,
    rx_angle: float,
    barrier: bool = True,
) -> QuantumCircuit:
    circuit = QuantumCircuit(num_qubits)

    for _step in range(num_trotter_steps):
        circuit.rx(rx_angle, range(num_qubits))
        if barrier:
            circuit.barrier()
        for first_qubit in (1, 2):
            for idx in range(first_qubit, num_qubits, 2):
                # equivalent to Rzz(-pi/2):
                circuit.sdg([idx - 1, idx])
                circuit.cz(idx - 1, idx)
        if barrier:
            circuit.barrier()

    return circuit

def mirror_circuit(circuit: QuantumCircuit) -> QuantumCircuit:
    mirror_circ = circuit.copy_empty_like()
    mirror_circ.compose(circuit, inplace=True)
    mirror_circ.barrier()
    mirror_circ.compose(circuit.inverse(), inplace=True)
    mirror_circ.measure_active()
    return mirror_circ
num_qubits = 20
observables = [
    SparsePauliOp("I" * ((num_qubits - 1) - q) + "Z" + "I" * q)
    for q in range(num_qubits)
]

# Free parameters of the demonstration circuit: the number of Trotter steps
# sets the circuit depth, and rx_angle is the transverse-field rotation angle
# applied in each step (pi/4 makes the dynamics non-Clifford)
num_trotter_steps = 5
rx_angle = np.pi / 4

circuit = construct_ising_circuit(
    num_qubits, num_trotter_steps, rx_angle, barrier=False
)
mirrored_circuit = mirror_circuit(circuit)
mirrored_circuit.draw(
    "mpl", fold=-1, scale=0.3, idle_wires=False, measure_arrows=False
)

ステップ2：量子ハードウェアでの実行向けに最適化する​

2.1 該当する場合は代替較正を使用する​

IBM® は、一般的なユースケースで良好な性能が得られるよう、QPU を定期的に較正しています。ただし、一部のワークロードは、パラメーターが異なる形で調整された命令の恩恵を受けます。詳細については、Specially calibrated instructions を参照してください。

このチュートリアルでは、slow_gates_ac と呼ばれる代替の較正データセットを使用します。この較正には、より遅い cz ゲートが含まれ、2準位系（TLS）のバイアスを変調して、デバイスのエラーを時間経過に対して安定させます。これらの変更は、学習したノイズモデルに依存するエラー緩和手法に有益です。slow_gates_ac 較正は Heron QPU でのみ利用できます。Nighthawk QPU で実行する場合は、代わりに slow_gates を使用してください。

from qiskit_ibm_runtime import QiskitRuntimeService

service = QiskitRuntimeService()
# Use slow_gates_ac because this tutorial uses a noise-learning-based mitigation method
backend = service.backend("ibm_kingston", calibration_id="slow_gates_ac")

2.2 リアルタイムのデバイスベンチマークを実行する​

トランスパイルで最も重要な段階の1つがレイアウト選択で、回路内の仮想量子ビットをターゲットデバイス上の物理量子ビットにマッピングします。良いレイアウトは、必要な SWAP 操作の数を最小限に抑え、回路を最も性能の高い量子ビットに配置します。そのため、初期レイアウトの品質は結果の品質に大きく影響することがあります。

すべての IBM QPU では、量子ビットの現在の性能を報告する定期的なベンチマークルーチンが実行されます。報告されるのは、緩和時間（T1T_1T1​）、コヒーレンス時間（T2T_2T2​）、読み出しエラー、1量子ビットおよび2量子ビットゲートのエラーです。Qiskit トランスパイラーは、レイアウト選択の際にこれらの指標を使用します。

しかし、超伝導量子ビットの特性はより短い時間スケールでドリフトすることがあり、TLS として知られる一過性の欠陥によって、較正時には良好だった量子ビットが一時的に劣化することがあります。トランスパイラーが古い情報を使用すると、最適なレイアウトを選択できません。したがって、レイアウトを選択する前に、QPU 時間を少し使ってデバイスの特性を調べる価値があります。

詳しい手順については、Refresh backend properties with real-time benchmarking チュートリアルを参照してください。 特性評価スイートは、複数の実験を構築し、複数のジョブを送信し、結果をフィットします。このプロセスには合計で数分かかることがあります。各段階が実行中に進行状況を出力するよう、INFO レベルのログを有効にしてください。

import sys
import logging

logger = logging.getLogger("qiskit_device_benchmarking")
logger.setLevel(logging.INFO)
logger.addHandler(logging.StreamHandler(stream=sys.stdout))

2.4 回路のタイミングを可視化する​

回路内の命令に加えて、量子ビットのアイドル時間や非効率な命令の配置を見つけるために、回路のスケジュールを可視化したい場合があります。ドライランモードを使用すると、IBM Quantum Compute Service から最も詳細で正確なタイミング情報を取得できます。

このチュートリアルの回路は静的なので、そのスケジュールはあまり参考になりません。回路とバックエンドのプロパティから、たとえば Qiskit に組み込まれたタイムラインドロワーを使って、同様のタイミング情報をローカルで取得できます。このチュートリアルでは、タイミング情報を要求して可視化する方法を示すために、このステップを含めています。サービスからのタイミング情報は、動的回路で最も役立ちます。動的回路には、回路途中の測定、条件付き操作、フィードフォワードが含まれ、測定結果のブロードキャストや分岐の決定といった暗黙の操作が加わります。これらの操作のタイミングは、回路とバックエンドのプロパティだけでは決定できません。

詳細については、Visualize circuit timing を参照してください。 スケジュールされた回路のタイミングは Sampler と Executor のジョブでのみ利用できるため、次のセルでは Sampler を使用してドライランモードで回路を送信します。ドライランモードで送信したジョブは、実際の QPU では実行されず、課金されません。

from qiskit_ibm_runtime.executor_sampler import Sampler

# Request timing information in the result metadata

ステップ3：エラー緩和を適用してローカルでテストする​

3.1 回路をクリフォード化する​

一般的なノイズありシミュレーションのコストは量子ビット数に対して指数関数的に増加し、ほとんどのノートパソコンでは約32量子ビットを超えるシミュレーションはできません。そのため、まず回路をクリフォード回路に変換します。スタビライザーシミュレーターなら、これをはるかに効率的に処理できます。この変換では各回転角をクリフォード角に丸めるため、シミュレートされる回路は元の回路を再現するのではなく近似するものになります。

from qiskit.transpiler import PassManager
from qiskit_ibm_runtime.transpiler.passes import ConvertISAToClifford

clifford_circuit = PassManager([ConvertISAToClifford()]).run(isa_circuit)
clifford_pubs = [(clifford_circuit, isa_observables)]

3.2 TREX を併用した PEC を適用する​

特定の実験に対して、コストと精度のバランスが取れたエラー緩和手法を選択するのは難しい場合があります。select-error-mitigation AI エージェントスキルを使用すると、ワークロードに対して利用可能な手法を分析できます。このスキルは、各手法が選択されたかどうかとその理由を説明する要約レポートを提示します。

詳細については、Qiskit AI skills GitHub リポジトリを参照してください。 このチュートリアルでは、AI エージェントなしで完了できるよう、TREX を併用した PEC を直接使用します。

PEC は、オブザーバブルの期待値を計算するときに量子ノイズを緩和する手法です。理想的な条件下では、PEC は期待値の不偏推定値を生成できます。2量子ビットゲートの各レイヤーのノイズを学習し、平均してそのノイズの逆を適用する回路のアンサンブルを実行します。PEC はパウリツワーリングを使用してノイズをパウリチャネルに整形し、効率的に学習および反転できるようにします。

実際には、PEC の精度は学習したノイズモデルの精度を超えません。スパース Pauli-Lindblad モデルには、隣接する量子ビット上の1量子ビットおよび2量子ビットのエラー項しか含まれず、離れた量子ビット間のクロストークや時間相関のあるエラーなどの影響を完全には捉えられません。また、デバイスのノイズはノイズ学習から実行までの間にドリフトすることもあります。PEC は、モデルが見逃したノイズを打ち消さず、モデルが過大評価したノイズを過剰に補償します。そのため、緩和された結果も、どちらの方向にも理想値からずれることがあります。

TREX は測定エラーを緩和する手法で、パウリオブザーバブルの期待値を推定するときに役立ちます。測定ツワーリングを利用し、読み出しエラーの遷移行列を対角化して、反転しやすくします。TREX は、ゼロ状態に初期化されたツワールされた較正回路を測定することで、対角ノイズチャネルから再スケーリング項を学習します。 Estimator のオプションを設定することで、PEC と TREX の両方を有効にできます。このチュートリアルでは、qiskit-ibm-runtime v0.50.0 で導入された、Qiskit の SamplerV2 および EstimatorV2 インターフェースのクライアントサイド実装を使用します。これらのクライアントサイドのプリミティブは、前処理と後処理の大部分をローカルで実行し、実行は Executor プリミティブに委任します。プリミティブをクライアントサイドで実行すると、透明性が高まり、デバッグ時のフィードバックが速くなり、より細かく制御できます。

クライアントサイドのプリミティブは、従来のサーバーサイドのプリミティブと同じ API を実装しています。そのため、通常は import 文を変更するだけで、クライアントサイドのプリミティブに切り替えることができます。 INFO レベルのログを有効にすると、クライアントサイドの前処理と後処理の進行状況を確認できます。

3.3 ノイズモデルを学習し、クリフォード化した回路を実行する​

PEC と TREX はどちらもノイズ学習を必要とし、これは NoiseLearnerV3 で行えます。手順は次のとおりです。

  1. 回路内の一意な2量子ビットゲートレイヤーと測定レイヤーを、それぞれ Pauli-Lindblad プロトコルと TREX プロトコル向けに見つけます。

  2. レイヤーを NoiseLearnerV3 に渡して、ノイズモデルを学習します。

  3. 学習したノイズモデルを Pauli-Lindblad マップに変換します。

Estimator は、事前に学習した TREX ノイズモデルを使用しません。代わりに、独自の TREX 学習を実行します。ノイズありシミュレーションでは学習した読み出しモデルを使用するため、次のコードではとにかく両方のモデルを学習します。

NoiseLearnerV3 の詳細については、Noise learning helper を参照してください。 ノイズ学習実験に加えて、クリフォード化した回路を QPU で実行します。このステップは常に必要というわけではありませんが、ステップ 3.4.4 のシミュレーション結果との比較対象になります。両者の間でノイズプロファイルがドリフトする量を最小限に抑えるため、両方をバッチで実行します。

3.4.4 シミュレーション結果を比較する​

3つのシミュレーションでの各1量子ビット ZZZ オブザーバブルの期待値を、ステップ 3.3 での同じクリフォード回路に対する緩和なしの QPU 結果とともにプロットします。この回路はミラー回路なので、すべての理想値は 1 です。エラーバーは、Estimator が各値について報告する標準誤差を示します。

緩和なしのシミュレーションが緩和なしの QPU 結果に近いほど、学習したノイズモデルがハードウェアをよく表しています。緩和ありの実験に QPU 時間を費やす前に、この比較をチェックとして使用してください。2つの結果が大きく食い違う場合、PEC もハードウェア上で理想値に近づく可能性は低いでしょう。その場合は、ノイズモデルを再学習するか、別のレイアウトを選択することを検討してください。ランダム化の回数を増やしたり、追加のレイヤーペア深さを使ったりするなど、NoiseLearnerV3 のオプションを変えてノイズモデルを再学習し、一致が改善するかを確認することもできます。たとえば、ステップ 3.3 でこのチュートリアルは num_randomizations をデフォルト値の 32 ではなく 64 に設定しています。これは、追加のランダム化によってこの回路での一致が改善したためです。

NoiseLearnerV3 は標準的な学習プロトコルを実行します。学習実験を完全に制御するには、Qiskit noise learning で独自の実験を構築できます。

3.5 使用量を見積もる​

4.1 セッションを初期化して較正を実行する​

QPU の較正では、量子ゲートや操作を駆動する電気信号を定義する多くのパラメーターが最適化されます。較正ジョブは、ユーザーのジョブの合間に一日を通して実行されますが、アクティブなセッション中には実行されません。これらのパラメーターは短期間でドリフトすることがあります。最良の結果を得るには、セッションの開始時、または長時間実行されるセッションでは定期的に、較正をトリガーすることを検討してください。

現在サポートされているのは読み出しの較正のみで、実時間で約5分かかります。

緩和ありと緩和なしのハードウェア結果を、理想値とともにプロットします。この回路はミラー回路なので、すべての理想値は 1 であり、各点と破線との距離が残りのエラーを示します。理想値からの残りのずれは、上でも下でも、PEC の統計的不確かさと、ステップ 3.2 で説明した学習済みノイズモデルの限界を反映しています。

結果をさらに改善するには、次の方法を試せます。

  • ショット数またはランダム化の回数を増やして、緩和された推定値の統計的不確かさを減らします。コストは PEC のサンプリングオーバーヘッドに応じて増加します。

  • ノイズのドリフトの影響を減らすため、同じセッション内で、実験の直前にノイズモデルを再学習します。

  • NoiseLearnerV3のnum_randomizations、shots_per_randomization、またはlayer_pair_depthsオプションを増やすことで、ノイズ・モデルをより正確に学習します。学習したレートの誤差は緩和後の結果にバイアスを与え、PECのショット数を追加してもこのバイアスは取り除けません。

  • 非マルコフ誤差チェックを追加して、学習したノイズ・モデルでは記述できない非マルコフ誤差によって破損している可能性が高いショットを検出します。その後、ポストセレクションでそれらのショットを破棄します。ノイズ・モデルを学習する際にも、NoiseLearnerV3のbit_flip_checksオプションを使って同じチェックを適用してください。そうしないと、学習したモデルにポストセレクションが実験から取り除く誤差が含まれてしまい、PECがそれらを過剰に補償します。ポストセレクションを厳しくするほど破棄されるショットが増えるため、精度の向上と残すショット数のバランスを取ってください。

4.3 ハードウェアの結果とシミュレーションの結果を比較する​

ステップ3.4では、ローカル・シミュレーションを使って、PECとTREXで結果がどの程度改善される可能性があるかを事前に確認しました。その結果をQPUの結果と比較します。シミュレーション上の改善とハードウェア上の改善が近ければ、QPUの時間を使う前に、このワークロードに対する緩和設定をローカル・シミュレーションで評価できることになります。

この比較は、次の2つの理由により近似的なものです。

  • シミュレーションはステップ3.1のクリフォード化した回路を実行しますが、ハードウェアのジョブは元の回路を実行します。

  • シミュレーションはステップ3.3で学習したノイズ・モデルを使用しますが、緩和を行うハードウェアのジョブはステップ4.2で更新したノイズ・モデルを使用します。

4.4 実行スパンを確認する​

ゲート・ツワリングなど、複数の構成を持つ回路を送信した場合、IBM Quantum Compute Serviceはすべての回路構成を必ずしも同時に実行するわけではありません。代わりに、それらをチャンクにまとめ、ショット・ループごとに1つのチャンクを実行します。ショット・ループとは、量子ハードウェア上での1回の実行ラウンドであり、チャンク内のすべての回路が要求されたショット数だけ実行されます。

実際のQPUに送信されるすべてのジョブには、ハードウェアに送信できるパルスへの変換など、古典的な前処理が必要です。この前処理は並列に実行できるため、サービスは複数のジョブを同時にキューから取り出して開始します。しかしQPUは、一度に1つの作業単位しか処理できません。そのため、ジョブが複数のチャンクを生成する場合、それらは他のユーザーのジョブのチャンクと交互に実行されることがあり、各チャンクはQPUで順番を待つ必要がある場合があります。

ジョブ結果のメタデータには、各チャンクのQPU実行タイミングが記録されています。次の可視化では、ジョブ内のチャンクの実行の間に大きな間隔があるかどうかがわかります。間隔が実験の許容範囲より広い場合は、ジョブを再実行するか、ワークロードにQPUへの排他的アクセスを与えるsession実行モードの使用を検討してください。

詳細については、実行スパンの表示を参照してください。
